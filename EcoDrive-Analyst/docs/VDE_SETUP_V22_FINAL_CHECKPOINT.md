# VDE Setup v2.2 - Final Stable Contract

## Purpose

VDE Setup v2.2 is the stable engineering workflow for creating, resolving,
reviewing, saving, and reloading traceable vehicle-demand scenarios. The
product-facing name is **VDE Setup**. The v2.2 identifier remains the
historical implementation checkpoint.

## Architecture

The Streamlit interface owns draft editing and user navigation. The canonical
state, resolver, preview, report, and persistence services own the engineering
contract. Preview and comparison consume the resolved result; they do not run a
second physics model.

## Workflow

1. Select a baseline and apply corrections to create the effective baseline.
2. Define requested proposals in the Proposal Matrix.
3. Enter and apply domain inputs.
4. Resolve Walk From lineage in proposal order.
5. Validate and preview the resulting snapshots.
6. Review engineering comparison, roadload, cycle analysis, and audits.
7. Review the DB save payload, save selected ready proposals, and reload their
   persisted history.

Supported domains are Mass, Tire, Aero, Transmission, Brake, Axle & Hubs, and
Parasitics.

## Baseline And Lineage

Printed values are the selected baseline values. Corrections produce the
effective baseline consumed by proposals. Each proposal resolves from its Walk
From snapshot, not always from the original baseline. A later proposal therefore
inherits the resolved values and metadata of its declared predecessor.

## Mass Contract

Mass resolution publishes a canonical VDE mass and tire calculation mass.

- EPA/TWC: VDE mass is the resolved regulatory mass and Mass owns the tire
  calculation mass.
- GVWR: loaded vehicle mass is curb plus payload; it is both VDE mass and tire
  load mass.
- GCWR: vehicle loaded mass is GCWR minus trailer mass; VDE mass is GCWR and
  tire load mass is the vehicle loaded mass. Trailer ABC enters roadload once.

## Tire Contract

Tire proposals resolve identity, RRC, pressure inputs, and tire ABC against the
canonical mass supplied by Mass. A tire DB test load is a tire test-condition
attribute; it is distinct from the vehicle tire calculation mass. Full SAE
lookup requires a compatible source tire contribution and never applies an
absolute target tire ABC against an implicit zero source.

## Transmission Contract

Transmission may preserve measured TOTAL and recalculate NET, or apply a vehicle
change to TOTAL as explicitly selected. In coastdown-share mode:

```text
ABC_TRANS_est = share x Walk From ABC_TOTAL
ABC_TOTAL remains fixed
ABC_NET = final ABC_TOTAL - ABC_TRANS_est
```

The share is coefficient-by-coefficient and is not a scale factor for inherited
Transmission ABC.

## Roadload And Preview

Roadload comparison can display TOTAL, NET, or both. Cycle analysis consumes a
physical cycle and the resolved snapshot. UI readiness, preview validation, and
audit status are derived from the same resolution result.

## Save And Reload

Save is append-only for ready selected proposals. Save records include resolved
snapshots, provenance, metadata, lineage, and warnings needed for reproducible
reload. Preview is not persistence.

## QA

QA uses deterministic synthetic fixtures and a separate database under
`data/qa/`. The production/local database is not regenerated by QA seed paths.

## Known Approximations

- The pressure-only fallback uses the documented generic sensitivity when a full
  source tire curve is unavailable.
- Component repository mocks are synthetic QA fixtures, not production component
  catalogs.

## Deferred Capabilities

Temperature and ambient-pressure roadload conditions are deferred. The intended
future boundary is:

```text
DB reference roadload
  -> Condition Correction Core
  -> temporary derived scenarios
  -> Comparison Report
```

Derived conditions should not create permanent DB rows by default. Comparison
Report consumes resolved scenarios; it must not become a second physics engine.
